# A-Society: Project Log

## Scope Tags

| Tag | Meaning |
|---|---|
| `[S]` — Small — single-session maintenance change (one to two files) |
| `[M]` — Medium — multi-step change within a single phase |
| `[L]` — Large — multi-phase or multi-file strategic change |
| `[LIB]` — Library — creates or modifies `general/` content; scope additions require Owner approval |
| `[MAINT]` — Maintenance — a-docs change within Curator authority; no Owner proposal needed |
| `[ADR]` — Direction decision involved; requires Owner-level scope |
| `[RUNTIME]` — Runtime-root executable change; routes through the TA and executable developer nodes when implementation is required |
| `[SITE]` — Public documentation site change under `site/`; involves the Technical Writer |
| `[OUTREACH]` — Outreach work; involves the Marketing Lead; nothing is published without the human's approval |

Tags may be combined: `[M][LIB]`, `[S][MAINT]`, `[L][LIB][ADR]`.

## Current State

**Status:** Framework at 0.3.3, the `a_society_version` in `CHANGELOG.md`; changes since then are listed under `[Unreleased]`. `general/` is an explicit two-tier library — universal layer at the `general/` root and category layer at `general/project-types/<type>/`; new category folders remain Owner-approved scope decisions. The a-docs scaffold manifest is the runtime-owned `$A_SOCIETY_RUNTIME_ADOCS_MANIFEST`, shared by runtime initialization and runtime health checks. The runtime offers **Update** only when a project is behind by a release line (the minor version while on 0.x, the major version from 1.0 on). Upstream feedback reports label every framework-improvement candidate universal, category-shaped, or project-specific; the runtime writes them to the workspace's `.a-society/feedback/` folder, and operators submit them as pull requests that add them to `$A_SOCIETY_FEEDBACK_DIR`. `runtime/` is the sole executable root: a local web server and browser UI that runs each role turn through LLM APIs or a supported host coding agent (agent mode; Claude Code today). The runtime resolves two roots, the A-Society checkout it runs from and the workspace (by default the checkout's parent; `A_SOCIETY_WORKSPACE` sets it explicitly), so a dev checkout's runtime can run on a test port against a scratch workspace. A-Society development happens in a dev checkout such as `a-society-dev/`, and the `a-society/` checkout the main runtime runs from stays on `main` (`$A_SOCIETY_AGENTS`). The executable architecture is a single standing reference at `$A_SOCIETY_EXECUTABLE_ARCHITECTURE`; the runtime placement standard keeps contracts in `runtime/contracts/`, server code in `runtime/src/` capability folders, the browser UI in `runtime/ui/`, and browser-safe shared code in `runtime/shared/`. Eight roles: the Owner; the Curator; the Technical Architect, design authority for the executable layer (its role template sits under the executable project-type category in `general/`); three executable developers (Framework Services, Orchestration, and UI); the Technical Writer, who owns the public documentation site in `site/` (a-society.dev); and the Marketing Lead, who plans outreach under hard disclosure rules and publishes nothing without the human's approval. `README.md`, `assets/`, and `site/` are public presentation surfaces, separate from both work product and agent documentation.
